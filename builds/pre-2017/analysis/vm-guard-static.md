# Статическая проверка VM-gate в позднем capture

Дата анализа: 2026-10-03. Все выводы сделаны из сохранённых файлов; этот анализ не запускал EXE/DLL и не менял бинарные данные.

## Результат

Точный участок, который выводит `Sorry, this application cannot run under a Virtual Machine.`, по имеющемуся capture локализовать нельзя. Строка найдена сканером в `MEM_PRIVATE` по адресу `0x181E4FE220`, то есть в области процесса вне образа `jvm.dll` (`ImageBase=0x5A970000`, `Size=0x1DDA000`). Поток `26312` был приостановлен на timeout: его системный RIP `0x7FFE...` находится вне JVM; скрипт сохранил только отсканированные qword-кандидаты стека, а не сырые страницы стека/частной памяти с инструкциями и call chain.

Строка начинается по `RSP + 0xA18`. Предшествующий qword по `RSP + 0xA10` равен RVA `0x1C08320` относительно JVM image. Это лишь соседнее значение стека, не подтверждённый return address. RVA `0x1C08320` попадает в высокоэнтропийный `.vmp1`; линейный Capstone decode даёт невалидные инструкции. Другие близкие кандидаты `0x1D4AE45` и `0x1C2B8BD` также лежат в packed/virtualized code и не дают пригодной линейной дизассемблировки. Кандидаты `0xB4457F` и `0xB447B5` указывают на заполнение `INT3`, значит не являются исполняемыми return sites в данном image.

В `analysis/dynamic-capture/cpuid-candidates.json` есть полноценный читаемый CPUID участок по RVA `0x76E698–0x76E83B`, в обычном `.text`. Он сопоставляется с HotSpot x86-64 `VM_Version` CPU-feature discovery: лист 0 собирает vendor ID (`GenuineIntel`/`AuthenticAMD`), лист 1 проверяет family/model/features, затем лист 7 и биты поддержки инструкций. Здесь не обнаружены hypervisor leaf `0x40000000`, сигнатуры гипервизоров, ветка на диалог или зависимость результата от гипервизорного признака. Поэтому этот CPUID xref нельзя считать искомым VMProtect gate.

Наблюдаемый диалог совместим с VMProtect `VMProtectIsVirtualMachinePresent` или собственной защитной проверкой, но это только гипотеза по строке и наличию `.vmp0/.vmp1`; точной атрибуции API или конкретного guard code нет. Официальная документация VMProtect описывает такую функцию как проверку VMware, Virtual PC, VirtualBox и Sandboxie, однако документация не доказывает, что именно её вызвал данный клиент.

## Что нужно для точной локализации

Нужен диагностический capture, который сохраняет read-only снимок страницы/страниц `MEM_PRIVATE`, где находится строка, и сырой стек основного потока до завершения процесса; для каждого pointer нужно проверять, что он указывает в реально исполняемую страницу и на границу декодируемого блока. Затем требуется связать адрес строки с инструкциями её передачи через аргументный регистр/буфер, установить адрес вызывающего кода и сопоставить условную ветку с результатом конкретной VM-check функции. Текущие данные такого сопоставления не дают.

Не следует менять HotSpot CPUID код на основании этого capture: он обслуживает обнаружение возможностей физического CPU. Идентификация нужной проверки и подтверждение её условия должны предшествовать любому изменению исследуемой копии.

## Источники

- OpenJDK 9u, `vm_version_x86.cpp`: https://github.com/openjdk/jdk9u/blob/master/hotspot/src/cpu/x86/vm_version_x86.cpp — историческая исходная ветка; описание структуры `get_processor_features` и `cpuid` stubs.
- OpenJDK, актуальная реализация `VM_Version::get_processor_features`: https://github.com/openjdk/jdk/blob/master/src/hotspot/cpu/x86/vm_version_x86.cpp — контрольное подтверждение назначения CPU-feature path; это не утверждение, что код современного master идентичен локальному JDK9.
- VMProtect User Manual: https://www.vmpsoft.com/vmprotect/user-manual — описывает `VMProtectIsVirtualMachinePresent`; использовано только для проверки допустимой гипотезы об источнике диалога.
- VMProtect Overview: https://www.vmpsoft.com/vmprotect/overview — описывает встроенную виртуализацию защищаемых фрагментов и почему случайные linear disassembly bytes в protected region не являются надёжной декомпиляцией.

## Уверенность

- **Высокая:** по данным capture строка находится в частной памяти, а не по найденному адресу в сохранённом образе JVM; stack scan сам по себе не является call stack.
- **Высокая:** CPUID-последовательность `0x76E698–0x76E83B` — CPU identity/features path, а не видимая проверка hypervisor.
- **Средняя:** anti-VM сообщение порождается VMProtect или интегрированной защитой. Признаки согласуются, но вызывающая функция не установлена.
- **Низкая/не установлена:** конкретный API, условная ветка, её RVA и любая точка изменения. На текущем evidence set их указывать нельзя.
