# Диагностическое исследование встроенной JVM — 03.10.2026

**Текущий результат на 04.10.2026:** полный офлайн-декодер подтверждён, все 30 715 защищённых class files восстановлены; opcodes методов нормализованы. Оба игровых/библиотечных архива успешно декомпилированы в 10 047 Java-файлов. Актуальная сводка — `restoration-status.md`. Отрицательные проверки ниже описывают ранние этапы; неправильный адрес stream-table `0x9f3d40` исправлен на `0xa2fd40`.

Пользователь явно разрешил диагностический запуск копии встроенной Java: `java.exe -version` и получение памяти JVM. Этот этап выполнен. Игра, лаунчер и вход в аккаунт не запускались. Оригинальный архив, распакованный клиент и работающая сборка Алекса не изменялись. Копия runtime — отдельный каталог на хосте, а не виртуальная машина или системная песочница.

## Полученный результат

Из собственного диагностического процесса сохранено отображение `jvm.dll` размером 31 301 632 байта без непрочитанных диапазонов. В исходном PE секции `.text` и `.rdata` не имели данных на диске; в снимке они заполнены и содержат читаемый машинный код/строки. Это позволяет изучать native загрузчик. Виртуализованные участки и таблица `.pdata` ещё не восстановлены; этот снимок нельзя считать готовой DLL для запуска.

Рабочий снимок: `dynamic-capture/jvm-watch-image-1791040961345929000.bin`; SHA-256 `7dbf906bfbcf0fe47372a235456307b34d178b2ed745fed00eb3f78c48b234ba`. Запись процесса/адресов — `watcher-run2-result.json`; разбор секций — `dynamic-capture/section-analysis.json`. Статическое PE-представление — `dynamic-capture/jvm-static-view.pe`. Воспроизводимый конвертер `analyze-jvm-capture.py` проверяет размер/SHA снимка и создаёт отдельное представление в `dynamic-capture/regenerated/`, не загружая DLL.

Статически восстановлены шесть пар `JLI_*`/hex-экспортов x86/x64 launcher. В читаемой `.rdata` по RVA `0x89abc0` найдена NUL-terminated строка `2G5teW9TkteWdMSx`. Формула **MD5(ASCII-имя функции + эта строка)** точно воспроизводит все шесть известных идентификаторов. Например, `JLI_Launch` → `9b490ffc0189e74ef6ca6c1079e09043`. Это доказанное преобразование имён экспортов, не доказанный ключ шифрования Java-классов.

Вторая соль `nUHDjbS59e4wF8Pr` по RVA `0x89abd8` также подтверждена кодом: `MD5(UTF-8(внутренний путь класса + salt2))` даёт имя payload. Повторно проверенные сопоставления: 784 записи `classes.jar`, 5 018 `libs.jar`, 13 844 JIMAGE. Среди них `com/stalcraft/StalcraftMod`, LaunchWrapper и Forge. Артефакты — `hash-mapping.json/md` и `classname-inventory.json/md`; это имена, а не декодированный байткод. Словарь расширяется отдельно по строгому разбору Java serialization.

По RVA `0x3ab230` восстановлен видимый блоковый шифр: AES-подобные 10 раундов/CBC, **нестандартная S-box и матрица обратного смешивания** `[82,183,13,233]`; арифметика GF(256) стандартная (`0x11b`), соответствие exp/log проверено для всех 65 536 пар. Локальный ключ — `e7488b845f71f6cccfb8945cc05d1f0d`. IV формируется из последних 16 байтов строкового аргумента с удалением `.class` при наличии; wrapper передаёт MD5-имя. Таблицы/константы записаны в `native-cipher-parameters.json`, извлечение повторяется `extract-native-cipher-parameters.py`.

`emulate-native-cipher.py` выполняет только читаемый участок машинного кода в Unicorn, на синтетической памяти, без загрузки DLL/Windows API. Эмуляция и Python-перевод дают одинаковые 1 552 байта для известной записи `java/lang/Object`; входной offset/size/SHA JIMAGE перепроверены. Однако результат не разбирается как обычный classfile. Префикс/энтропия и точное сравнение — `custom-cipher-object-result.json`. Вызов этого участка подтверждён во всех трёх backend — обычные файлы, JAR и JIMAGE (`native-classpath-cipher-boundary.md`).

Дополнительная ограниченная эмуляция раскрыла API-границы защищённых вызовов. Helper `0x3ab210` вызывает `NtClose`/`ZwClose` с аргументом `0x1ee7c0de`; при синтетическом `STATUS_INVALID_HANDLE` возвращает ноль. Это независимо воспроизведено из сохранённого снимка (`emulate-protected-helper.md`) и с чтением памяти собственной диагностической Java (`live-protected-offset-helper.json`). Postamble `0xf33409` вызывает `GetCurrentThread`; `0xf35d0a` вызывает `ZwSetInformationThread(-2, 0x11, 0, 0)` — путь скрытия потока от отладчика. Реальные API из эмулируемого кода не исполнялись, ответы подставлялись. Вторая трасса достигла API-границы, но не подтвердила весь возврат thunk (`live-protected-hide-thread-thunk.json`). Эти вызовы не передают буфер класса; данных за ещё одно преобразование payload в postamble нет.

Найден ещё один слой формата: собственные readers `ClassFileStream` (`0x3aa4c0`, `0x3aa620`, `0x3aa680`) преобразуют байты с использованием двух предыдущих байтов, вращения и таблицы `04bccaa83d737cadcaad5633735bc7da` по RVA `0xa2fd40`. Ранний адрес `0x9f3d40` был ошибкой вычисления RIP-relative address. Парсер сначала пропускает два байта и проверяет 16-битный marker `0xe629`, а не стандартный `CAFEBABE`. Все четыре reader проверены эмуляцией; слой успешно применён ко всем защищённым payload. Отдельно восстановлена перестановка opcodes в методах; подробности — `restoration-status.md`.

## Почему диагностический запуск не завершается

Обычный запуск скопированной Java с `-version`, запуск с отладчиком и наблюдение памяти без отладчика не напечатали версию. В private memory собственного дочернего процесса обнаружено сообщение:

> Sorry, this application cannot run under a Virtual Machine.

Таким образом, присутствует активная проверка виртуальной среды. По одному сообщению нельзя установить, какая именно особенность хоста её вызывает. Системные настройки виртуализации не менялись. Читаемый HotSpot CPUID-код оказался обычным определением CPU и его возможностей; конкретный условный переход VMProtect, вызывающий диалог, пока не найден. Офлайн-размотка синхронного стека по системным unwind-таблицам подтвердила цепочку через `USER32!MessageBoxW` до первого адреса возврата в JVM `0x1c2b8bd`; непосредственно перед ним в снимке — `call rax` по RVA `0x1c2b8bb` (`vm-dialog-unwind.md`). Другие сырые адреса из стека остаются кандидатами, а не доказанными кадрами.

Один эксперимент фильтровал CPUID в распознанных обработчиках VMProtect только в памяти собственного диагностического процесса. Сам фильтр предварительно проверен на доверенном Python-процессе, однако Java завершилась с `0xC0000005` (access violation). Причина не установлена; обход защиты не подтверждён. Изменённых EXE/DLL на диск не записывалось.

## Границы и воспроизводимость

- Перед выполнением проверялись SHA-256 всех 31 файла диагностической копии по `diagnostic-copy.json`.
- `capture-unpacked-jvm.py --self-test` проверил структуру событий отладчика/чтение памяти на доверенном собственном Python-процессе; `--execute` выполнял только разрешённую копию Java `-version`.
- `watch-jvm-memory.py --self-test` проверил запуск/наблюдение собственного дочернего процесса; `--execute` наблюдал PEB/modules и снимал память только созданной диагностической Java. Режим `--late` выявил сообщение об отказе и адреса собственного стека.
- По окончании завершались только процессы, созданные конкретной диагностикой. Другие Java-процессы и игра пользователя не затрагивались.
- `diagnose-cpuid-filter.py --self-test` проверил генерацию фильтра CPUID; `--execute` дал неуспешный результат, сохранённый в `cpuid-filter-result.json`.
- Снимки памяти и статические представления — исследовательские артефакты, не восстановленный runtime. В последующем офлайн-этапе Java-классы декодированы, opcodes исправлены и исходники получены; игровое выполнение и пересборка ещё не проверены.

Офлайн-восстановление ClassFileStream, нормализация opcodes и декомпиляция завершены. Следующие задачи — подготовка пересборки, восстановление обфусцированных имён/пакетов и проверка native/runtime-зависимостей. По сообщению пользователя о BSOD новая защищённая Java и эксперименты с памятью автоматически не запускаются; наблюдение записано в `windows-crash-observation-2026-10-04.md`.
