# Статическая проверка bundled native Java и признаков загрузчика

Проверены только байты `win64/java/bin/java.dll` и `win64/java/bin/server/jvm.dll`: PE-заголовки, импорт/экспорт таблицы, имена секций и ASCII-строки. DLL и EXE не загружались и не запускались. UTC-время ниже — PE COFF timestamp, не доверенная дата создания.

## `java.dll`

- Размер: 7,680 байт; PE x64; COFF timestamp `2017-09-14 22:03:00 UTC`.
- Импорты: `MSVCR120.dll`, `KERNEL32.dll`.
- PE export directory отсутствует (RVA 0, size 0).
- ASCII содержит PDB-путь: `c:\users\folken\documents\visual studio 2013\Projects\EmptyDll1\x64\Release\EmptyDll1.pdb`.
- Среди просмотренных ASCII-строк нет `read_derived`, `use_system_class_loader`, `load_dumped_event_classes`, `exbo`, `stalcraft`, `decrypt`, `encrypt`, `classloader`, `packed` или `hash`.

**Вывод:** малый размер, отсутствие exports и путь `EmptyDll1.pdb` согласуются с тем, что это не обычная полная Java native library, а созданный отдельно shim/placeholder. Это гипотеза о назначении; без кода нельзя подтвердить, какую роль DLL выполняет. Имя пользователя `folken` в PDB-пути само по себе не доказывает связь автора файла с авторами из `mcmod.info`.

## `server/jvm.dll`

- Размер: 12,961,792 байта; PE x64; COFF timestamp `2017-10-28 01:45:14 UTC`.
- Импорты включают системные DLL Windows, в том числе `KERNEL32`, `WS2_32`, `WINHTTP`, `OPENGL32`, а также `MSVCR120` и `MSVCP120`.
- Секции включают `.vmp0` и `.vmp1`; у `.vmp1` raw size 12,879,872 байта, энтропия около 7.954 бит/байт.
- ASCII содержит `VMProtect Software`, `VMProtect Software CA0`, `VMProtect Client ipn90641` и другие строки VMProtect.
- Таблица экспорта имеет 3,552 именованных экспорта. Имена выглядят как 32-значные hex-строки, например `00042da913b103c41ff1e9b8366a83a5` и `0005e97af70952adda826e9486ce8da7`; стандартные читаемые JVM export names в этой таблице не видны.
- Среди ASCII-строк нет `read_derived`, `use_system_class_loader`, `load_dumped_event_classes`, `exbo`, `stalcraft`, `decrypt`, `encrypt`, `classloader`, `packed` или `hash`.

**Вывод:** строки `VMProtect ...` — прямое свидетельство использования VMProtect-механизма/компонента в этом `jvm.dll`. Нестандартные секции и hex-имена exports согласуются с защищённой или преобразованной JVM и объясняют, почему стандартная статическая проверка не показывает обычные имена точек интеграции. Это не устанавливает, что именно код скрывает, и не доказывает конкретную пользовательскую функцию загрузки классов.

## Сопоставление с JAR payload

`classes.jar` содержит нулевые `.class`-записи и тысячи файлов с 32-hex-именами; top-10 крупнейших таких файлов имеют энтропию около 8 бит/байт и не распаковываются прямым gzip/zlib/raw-DEFLATE. Hex-экспорты `jvm.dll` показывают похожее внешнее именование, но связь этих экспортов с именами файлов в JAR не доказана. Ни одна из указанных функций загрузчика или расшифровки не нашлась в ASCII-строках этих двух DLL.

**Гипотеза:** bundled Java 9 могла быть модифицирована или использована как часть защищённого стартового окружения, способного обслуживать особый формат классов. Наблюдения позволяют считать это правдоподобным, но конкретная схема распаковки/загрузки и связь с opaque JAR payload остаются неизвестными. Штатность этого runtime не подтверждена.

## Расхождение версии GloomyCore

В `classes.jar!/mcmod.info` указано `GloomyCore` версии `0.1.1_[1.6.4]`; запись в `mods/asmdata/gloomyfolken.mods.core.main.GloomyCore.dump` указывает на класс GloomyCore версии `2.4.47_[1.6.4]`. Это расхождение двух разных наборов метаданных внутри кандидата; возможно, `mcmod.info` относится к legacy/другой вложенной записи, а ASM dump — к кэшированным или фактически используемым классам. Причина не установлена. Ни одну из этих цифр нельзя трактовать как версию самого клиента.
